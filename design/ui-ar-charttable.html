AR chart table — layout study

The desktop bezel and this are the same four regions — global-state, tools, selection, time — at two scales. Here they become world-locked slabs around a volumetric map table, with entity detail anchored to the entity itself. Nothing is head-locked except a single peripheral alert pip.

Read the anomaly path: the vessel is magenta on the table, its callout is anchored above it with a leader line, the same gap appears as a bracket on the body-locked scrub, and an unattended alert shows as a peripheral pip at ~20° eccentricity. One event, four consistent appearances, no text required to connect them.
Plan view · slab placementseated user, origin at head
Slabs sit at ±38° — clear of the table's footprint but outside the ±30° sustained-reading cone, which is deliberate. They are glanceable, not readable-while-working. Anything you must read while operating belongs on the table itself or in an anchored callout.

Body-locked = lazy follow with a 12° dead zone and ~400 ms ease, so it settles instead of chasing. Head-locked is used exactly once, for an unattended anomaly, and it dismisses on gaze. Everything else is world-anchored — that is the difference between an AR tool and a HUD strapped to your face.

For scale: the desktop mockup's 8.5px labels subtend roughly 0.2° at a normal monitor distance. AR labels must be about 6× larger angularly. This is the single biggest reason the desktop bezel cannot be ported pixel-for-pixel — it is an information-density change, not a styling change.

SubstrateBlack renders asPalette consequence
Video passthrough
Vision Pro, Quest 3		 real black The achromatic desktop palette ports almost directly. Smoked-glass slabs at ~90% opacity, near-white text, vivid accent in tiny areas. This mockup assumes passthrough.
Optical see-through
HoloLens, Magic Leap		 transparent The palette inverts. Additive displays cannot draw black — #06080a renders as nothing. Slab fills disappear; only emissive strokes and light text survive. You design in outline and glow, thicken strokes ~2×, and drop every dark surface. Legibility comes from stroke weight, not from contrast against a panel.
This is the decision to make before writing any XR code. If optical see-through is a target, the achromatic-near-black direction is wrong at the substrate level and needs re-deciding — not re-tuning.

The one architectural move that makes this cheap: define the four regions semantically in code — global-state, tools, selection, time — not as CSS positions. A desktop renderer maps them to edge rails; an XR renderer maps them to world-locked slabs. Same state, same managers, two presenters. Three.js already has WebXR built in, so the render path is not the hard part — the coupling of layout to CSS position is.
